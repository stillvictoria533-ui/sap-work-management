## 业务范围协议

多对象采用每行或每个分号子句一组带标签的业务键，例如：

```text
BELNR=1900000123 BUKRS=1000 GJAHR=2025
BELNR=1900000456 BUKRS=2000 GJAHR=2026
```

对应的两个业务对象独立保存。`document_keys` 保留为值索引，不再允许从中选取不同对象的字段交叉组合。独立值列表无法证明配对关系时不按顺序 zip；同一明确对象缺少必要字段时保留缺失状态，不借用另一对象的值。

已明确对象缺少的必要键可由工单提交人按既有对象键补齐一次，并记录 `data_object_completion_events`；不能修改既定键、加入新对象或更换系统。物料／单据 ID 保留既有数字零前缀兼容，组织、年度、语言条件与受理值逐字匹配。

旧 v1 范围的单对象或单一业务键列表仍可确定性校验。涉及多个字段和多个值时，不直接信任集合的笛卡尔积：服务器核对原受理材料 `source_hash`、受理事件，并确保重建值属于旧范围后，可从原始明确组合恢复关系。此过程沿用既有授权，不要求二次受理。原文无法证明关系或摘要不符时拒绝自动数据查询，后续消息不能把已冻结的值重新配对；需要补充关系证据并转人工核实。DDIC／源码能力仍服从原有对象与操作限制。

不新增数据库迁移，不重置既有租约、期限、尝试次数或查询账本。发布时仍需先停止并确认旧协调器退出，再同步服务端策略、本机可信运行包及 planner 提示词；本轮必须取得最终内容的发布确认。

## 验证与证据

本轮本地使用 Python 3.14.3、Node 24.21.0、SQLite。自动化命令、通过与跳过数量见 [verification.json](verification.json)。两项需要 PostgreSQL 行锁的原有测试及两项可选 CLI 能力测试按环境跳过，本轮不以此前发布的 PostgreSQL 通过结果替代对新代码的验证，也未连接真实 SAP 或模型。

新增回归覆盖：

- DS4、QS4、PS4 的正确组合与全部交叉组合，错误查询不落预留账本；中文标签、分号记录、数字 ID 兼容及组织键严格匹配。
- 按明确对象补齐缺失工厂／语言、拒绝按列表位置补齐、拒绝替换已定值；旧范围原文恢复、摘要不符拒绝及禁止后续消息重新配对。
- 未编辑日期的空→有、有→新日期、有→空刷新；主动改期与明确清空的冲突确认；独立排期草稿采用同样保护。
- 新建成功迟到不导航，活跃页面成功仍导航；版本查询保持权限且只读取必要字段。

真实浏览器使用两个独立管理员会话和一个顾问会话，连接临时 SQLite：

1. A 未改受理日期，B 设置 `2026-12-20`；A 刷新再受理，请求版本为 2，未附带 `estimated_completion_date`，保存日期仍为 `2026-12-20`。
2. A 草稿为 `2026-12-25`，B 更新为 `2026-12-22`；刷新后出现两个日期及选择按钮，确认前提交按钮禁用。明确采用 A 的改期后，请求使用版本 3，最终保存 `2026-12-25`。
3. 上述冲突界面在 390px 移动视口下无横向溢出。
4. 顾问新建请求实际返回 201，但人为延迟客户端接收；确认离开后释放响应，页面仍为 `/tickets`，未被拉回详情。

页面逻辑 harness 未渲染 DOM 的限制仍保留；以上浏览器核查另行覆盖实际 DOM、日期输入、按钮状态、网络参数及路由行为。
