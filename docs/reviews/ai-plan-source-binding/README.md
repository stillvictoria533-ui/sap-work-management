# AI 查询协议与源码类型绑定修复

状态：2026-10-30 候选修复及隔离 PostgreSQL 补测完成，等待用户确认后发布。基于 GitHub `main` 的 `d8546d0`，分支 `codex/ai-plan-source-binding-fix`。未部署应用、切换 Mac 后台运行包、修改现有工单或执行 SAP 查询。

## 最终行为

1. 模型输出 Schema 把 `kind` 限定为 `"" / fm / prog / class`，提示词明确各类型含义。兼容边界只将已知的 `function → fm`、`program → prog` 转换为标准值，再通过原有执行策略；未知类型、额外字段、无关选项和范围不匹配仍拒绝。
2. 原受理标题中已明确命名、但尚未绑定源码类型的对象，可以由可信执行器核验类型。模型只能提出原对象的源码查询，不能提供证明、选择元数据表、切换系统或调用内部核验操作。
3. 执行器对原对象做下表四次固定、精确、最多两行的元数据读取。四项回执完整、同轮同租约、五分钟内完成，且目录合计仅有一个函数/程序/类匹配时，服务端才填入缺失类型，并保存查询 ID、结果摘要和绑定审计。
4. 类型绑定后，源码请求重新经过原 `validate_plan`、服务端查询预留及执行器复核。元数据结果不进入业务证据列表，也不能作为工单分析回复的证据。正常回复仍必须引用本轮真实完成的源码/业务查询回执。

| 固定元数据表 | 返回字段 | 等值过滤 | 行上限 |
| --- | --- | --- | --- |
| DD02L | TABNAME | TABNAME=原对象，AS4LOCAL=A | 2 |
| TRDIR | NAME | NAME=原对象 | 2 |
| TFDIR | FUNCNAME | FUNCNAME=原对象 | 2 |
| SEOCLASS | CLSNAME, CLSTYPE | CLSNAME=原对象 | 2 |

DDIC 对象冲突、不同源码类型重名、重复行、接口类型、没有匹配或证据不完整，均不绑定类型。重名或没有匹配在本轮转人工；网络、身份、签名等失败仍按既有失败规则处理。

正文中的 JSON 参数名、GUID、后续消息和 SAP 返回不能增加可自动核验的对象。旧 scope 仅在原受理材料摘要、受理事件、系统/client 全部一致时补齐核验候选。标题之外的未定类型对象继续使用原“需要确认对象源码类型”门禁。

## 安全边界

- 不开放 PS4 `search`、`find-text`、SQL、任意 RFC、写入、接口执行或其他生产访问方式。内部 `source-type` 计划仍被普通模型计划校验拒绝；技术表不进入普通 `DATA_TABLES` 业务白名单。
- 四次核验都使用现有公司 `data` CLI、固定连接身份、精确 scope 签名、一次性令牌/ledger 和审计；参数、字段、过滤条件由程序决定，结果的对象、系统、client、投影、行数及内容摘要逐项复核。
- 核验共享本轮最多 8 次查询的原额度，每次读取都消耗一次；开始核验前还须保留一次实际源码读取额度。失败和旧查询不会清除或换取新额度。
- 保留 15 分钟租约、首次领取起 45 分钟期限、最后 5 分钟停止新查询、版本校验、人工抢先回复及功能停用门禁。绑定操作不改工单版本、状态、受理人或触发事件。
- PS4 类源码仍须提供原受理范围内的精确 method；核实类名不会授权整类读取。已绑定类型不被新结果或后续补充改写。
- 服务端只接受持有租约的可信执行器回执，SAP 返回始终是 `UNTRUSTED_EVIDENCE`。摘要用于一致性核对，不能单独作为外部来源证明；模型无工具、凭据或网关访问能力。
